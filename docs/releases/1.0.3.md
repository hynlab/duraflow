# Duraflow 1.0.3

Reliability fixes for the nine findings in the 2026-10-11 review of `3c6eb4d`,
plus the accumulated long-running-workflow and reply-resource lifecycle changes.

## Correctness fixes

- Direct calls and initial broadcasts share attempt/deadline reservation. A
  broadcast still publishes once; participant retries use the direct route.
- Task execution has bounded data consumers and an independent control/completion
  consumer. Cancellation, delegated callbacks, and the outbox continue while all
  execution slots are occupied. Each lane maintains its own round-robin cursor.
- New execution requests carry an absolute start deadline derived from schedule
  and overall timeouts. Workers reject expired claims and recheck journal time,
  ownership, and cancellation immediately before invoking user code, including
  after slow publication. Deadline settlement durably requests cancellation of
  the old attempt. Expired results retain the applicable timeout code.
- Valid task outcomes are committed even when the next replay snapshot exceeds
  the 16 MiB wire limit. The run becomes `BLOCKED` with `SNAPSHOT_LIMIT`; the input
  result is not quarantined. Oversize `describe()` responses return a summary
  with `details_omitted`, counts, and the blocked reason; full details remain in
  the journal. Internal output limits are distinct from malformed wire input.
- Archival resolves the exact requested run. Unknown or empty explicit run IDs
  return `NotFound`, preserving the current execution's history and result.
- External completion requires nonempty string `code` and string `message`
  fields for errors. SDK and worker validate before changing the outcome; an
  invalid callback leaves the delegation available for a corrected callback.
- Reusing an inbox message identity with different content is a permanent
  integrity error and is quarantined. Transaction/outbox conflicts retain their
  retry behavior.
- Automatic heartbeat renewal preserves explicitly reported progress.
- All protocol-2 journals expose versioned telemetry from indexed status
  projections and outbox timestamps. Missing/stale collection is reported as
  unavailable and `NaN`, with a collection-failure counter, rather than zero.

## Lifecycle improvements included

Completed run details and signal/tag deduplication records can move out of the
hot workflow document into transactionally coupled records. GC respects pending
outbox obligations, retention, active task leases, and message admission fences.
Signal epochs support bounded retry identities across continuation runs. Reply
subscription/producer caches support churn, cleanup, and pinning during native
sends. See [the lifecycle runbook](../long-running-workflows.md).

## Upgrade and operational contract

Execution protocol stays **2**. Message-journal schemas are now **PostgreSQL 4**
and **SQLite 3**. Stop old writers, back up each journal, initialize/migrate each
workflow/task/tag journal with the new binary, and restart the roles together.
Migrations preserve histories, inbox identities, and outstanding publications;
the telemetry backfill runs once during migration, not on health probes.
Rollback requires restoring the pre-upgrade database together with the old
binary. Do not run old binaries against the migrated schema.

Start deadlines are UTC timestamps generated by the workflow journal and checked
using the task journal's clock (database time on PostgreSQL). Journal hosts must
have synchronized clocks; the boundary is subject to their clock skew and the
small interval between admission and invocation. Existing pre-1.0.3 queued
envelopes do not acquire a start deadline retroactively. Reconcile those pending
attempts during the maintenance upgrade before resuming task consumers.
Result timeout, prevention of a new invocation, and cancellation of running code
are distinct guarantees. Already-running external effects still require domain
state/version guards and idempotency; synchronous functions remain cooperative.

`SNAPSHOT_LIMIT` preserves a recoverable checkpoint, not an unlimited-history
engine. Inspect the summary and retained journal, restore sufficient snapshot
capacity with a compatible runtime, then use audited `resume_blocked()`. Resuming
without resolving the limit blocks again. Completed tasks are reused on replay.
Use continuation and external payload references to keep new histories bounded;
automatic blob-backed snapshots are not introduced in this release.

`duraflow_runs` counts current workflow heads in the requested namespace (not
archived continuation generations). Outbox age covers the runtime's journal.
Broker-owned timer lag is not measured by protocol-2 journal telemetry and is
reported as `NaN`. `duraflow_telemetry_available`,
`duraflow_telemetry_failures_total`, and
`duraflow_telemetry_observed_timestamp_seconds` distinguish collection status.
Legacy outbox entries receive migration time as their first measured timestamp.

## Verification

Positive regressions cover exact/late deadlines with absent workers on memory and
SQLite, no first effect after workflow timeout, stalled pre-invocation
publication, unknown archive IDs, malformed callback correction, permanent vs
transient conflicts, status projection rollback, schema upgrades, and real 16 MiB
snapshot overflow on memory and SQLite. Saturation at both 1 and 8 slots is tested
with cancellation and external completion on memory and **real Pulsar/PostgreSQL**.

Release qualification also includes the complete native integration/fault suite,
physical PITR, the coverage gate, frozen codec compatibility, packaging checks,
and a real-service three-participant broadcast/continuation lifecycle soak.
See [release verification](../qualification-1.0.3.md) for measured results.
