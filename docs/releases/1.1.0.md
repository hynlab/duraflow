# Duraflow 1.1.0

## Activation-result message boundary recovery

Fixes the remaining defect from the independent 1.0.3 retest: a replay result
could fit the subprocess pipe limit but exceed the 16 MiB broker envelope after
the worker added metadata or child manifests. The uncaught `MessageSizeLimit`
previously caused repeated NACKs, leaving the workflow pending with an active
activation and no committed commands.

- The worker checks the final serialized `activation_result` and replaces an
  oversized decision with a bounded `blocked / ACTIVATION_RESULT_LIMIT` response.
- Response ID, key, run/activation IDs, and expiration are preserved. Publication
  must succeed before the original activation is acknowledged; transient delivery
  failures remain retryable with the same response identity.
- The engine's existing blocked transition releases the active activation without
  partially committing the oversized decision or discarding committed history.
- The process executor reserves 4 KiB below the wire limit for output-envelope
  overhead. Its default input budget remains 16 MiB. Oversized subprocess output
  returns a bounded typed failure and the healthy child process can be reused.
- The final worker check remains authoritative, including for inline/custom
  executors and child-manifest expansion.

`resume` retries a blocked activation; it does not itself solve the size limit.
The response-size cause must be addressed in a replay-compatible deployment.
See [operations](../../guide/6_operations.md#110-activation-result-size-recovery).

## Compatibility

Execution protocol 2 and PostgreSQL schema 4 / SQLite schema 3 are unchanged from
1.0.3. Upgrades from earlier versions still require the
[1.0.3 migration procedure](1.0.3.md). Epoch-less signals retain the compatibility
limit of 10,000 chain-wide IDs; long-lived signal senders must preserve both the
original `signal_epoch` and `signal_id` when retrying. Pre-1.0.3 queued task messages
do not acquire start deadlines retroactively.
